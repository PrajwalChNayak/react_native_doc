# Example: expo-native-module

A local **Expo Module** in Kotlin and Swift, written with the **Expo Modules API** and
autolinked into an SDK 57 app.

> **Toolchain:** Expo SDK 57 · React Native **0.86.3** · **requires a development build**. It
> does not run in Expo Go.

## Where the module came from

It was generated by the real tool, not written from memory:

```bash
npx create-expo-module@57.0.1 device-metadata --local --name DeviceMetadata \
  --package expo.modules.devicemetadata --platform apple android \
  --features Constant Function AsyncFunction Event View --barrel
```

One honest note: the generator printed `Couldn't download the versioned template from npm,
falling back to the latest version.` The sources below are therefore from the latest
`expo-module-template`, not one pinned to 57. They type-check and autolink against SDK 57
(see Verify), but compare with a fresh generator run if you need the exact 57 template.

```text
modules/device-metadata/
├── expo-module.config.json     tells autolinking which classes are modules
├── index.ts                    barrel file (from --barrel)
├── src/
│   ├── DeviceMetadataModule.ts     requireNativeModule<...>('DeviceMetadata')
│   ├── DeviceMetadataView.tsx      requireNativeView('DeviceMetadata')
│   └── DeviceMetadata.types.ts
├── android/…/DeviceMetadataModule.kt   Kotlin
│   └── …/DeviceMetadataView.kt
└── ios/
    ├── DeviceMetadataModule.swift      Swift
    ├── DeviceMetadataView.swift
    └── DeviceMetadata.podspec          depends on ExpoModulesCore
```

## The Expo Modules API, as generated

Both platforms declare the same module with the same DSL:

```kotlin
class DeviceMetadataModule : Module() {
  override fun definition() = ModuleDefinition {
    Name("DeviceMetadata")
    Events("onChange")
    Constant("PI") { Math.PI }
    Function("hello") { "Hello world! 👋" }
    AsyncFunction("setValueAsync") { value: String ->
      sendEvent("onChange", mapOf("value" to value))
    }
    View(DeviceMetadataView::class) {}
  }
}
```

```swift
public class DeviceMetadataModule: Module {
  public func definition() -> ModuleDefinition {
    Name("DeviceMetadata")
    Events("onChange")
    Constant("PI") { Double.pi }
    Function("hello") { return "Hello world! 👋" }
    AsyncFunction("setValueAsync") { (value: String) in
      self.sendEvent("onChange", ["value": value])
    }
    View(DeviceMetadataView.self) {}
  }
}
```

There is **no Codegen spec**. That is the main difference from a React Native TurboModule, where
a TypeScript spec generates abstract native classes. Here the native DSL is the source of truth,
and the TypeScript side declares the shape by hand in `DeviceMetadataModule.ts`. See
[Expo Modules vs TurboModules](../../content/expo-native-code/vs-turbomodules.md).

## Why it needs a development build, and how the app checks

Expo Go ships a fixed set of native modules and cannot load yours, so
`requireNativeModule('DeviceMetadata')` throws there. `App.tsx` checks with
`requireOptionalNativeModule('DeviceMetadata')`, which returns `null` instead of throwing, and
only then requires the module.

It deliberately does **not** use `Constants.executionEnvironment === 'storeClient'`. The
installed expo-constants types document `StoreClient` as *"Expo Go or a development build built
with expo-dev-client"*, so that check is also true inside the development build that *can*
load the module.

## Run it

```bash
npm install
```

```bash
npx expo run:android
```

`expo run:android` generates `android/` because it is missing, compiles the Kotlin and installs
the app. iOS uses `npx expo run:ios` and needs **macOS with Xcode**. Native changes are not
picked up by Fast Refresh; rebuild after editing Kotlin or Swift.

## Verify

These were run on this project on Windows with Node 22.13.0:

| Check | Result |
| --- | --- |
| `npm run tsc` | exit 0 |
| `npm run check-deps` | `Dependencies are up to date` |
| `npm run config:public` | resolves; `sdkVersion: 57.0.0` |
| `npx expo-modules-autolinking resolve --platform android` | finds `device-metadata` |
| `npx expo-modules-autolinking resolve --platform apple` | finds `device-metadata`, pod `DeviceMetadata`, class `DeviceMetadataModule` |
| `npm run export` | **584 modules** → `index-*.hbc` **1.4 MB** |

**NOT RUN on this host:**

- **Kotlin compile:** `expo run:android` needs an Android SDK with the platform SDK 57 targets.
  It was not run, so the Kotlin is unverified beyond autolinking resolving it.
- **Swift compile:** needs macOS with Xcode.

The native sources are exactly what the generator produced, and nothing was hand-edited, but
**no native build of this example was performed**.
