You can write the logic of an iOS TurboModule entirely in Swift. What you cannot do is make
Swift the thing React Native talks to. The generated interface is an Objective-C protocol whose
methods take and return C++ types, and Swift cannot adopt it.

This page is about that boundary: exactly where it sits, how thin you can make the layer that
crosses it, and what the rest of the iOS build needs. It assumes you have read
[TurboModules End to End](turbomodules-end-to-end.md), which walks both platforms once.

## Why the Objective-C++ layer exists

Codegen writes two things into `ios/build/generated/ios/<name>/<name>.h`:

- `@protocol NativeCalendarSpec`, with one Objective-C method per spec method **plus** a
  `getTurboModule:` requirement that returns `std::shared_ptr<facebook::react::TurboModule>` and
  takes `const facebook::react::ObjCTurboModule::InitParams &`.
- `class NativeCalendarSpecJSI`, a C++ class in namespace `facebook::react` that holds the JSI
  bindings.

Swift has no way to express either of those signatures. Apple's Swift/C++ interoperability does
not cover `std::shared_ptr` of a polymorphic C++ type reached through an Objective-C protocol,
and the header itself cannot be imported into Swift because it is C++ rather than Objective-C.

So the layering is fixed:

| File | Language | Job |
| --- | --- | --- |
| `Calendar.swift` | Swift | All of your logic. Knows nothing about React Native. |
| `<App>-Swift.h` | generated by Xcode | Exposes the Objective-C-visible surface of your Swift |
| `RCTCalendar.h` / `.mm` | Objective-C++ | Adopts the generated protocol, forwards to Swift |

The `.mm` file is small and mechanical: one `getTurboModule:`, one `moduleName`, and one
forwarding method per spec method. It is not where your logic goes, and it should not grow.

> [!NOTE] You can skip Swift entirely
> If you are comfortable in Objective-C++, put the logic straight in `RCTCalendar.mm` and delete
> the Swift file. That removes a file, a bridging header and a generated header from the build.
> The Swift split is worth it when the logic is substantial or when your team writes Swift; it
> is overhead when the module is four short methods.

## The four files, in order

### 1. The Swift class

```swift title=ios/AwesomeProject/Calendar.swift
import EventKit
import Foundation

// NSObject and @objcMembers are both required: only NSObject subclasses appear
// in <App>-Swift.h, and only @objc members appear on them.
@objcMembers
public class Calendar: NSObject {
  private let store = EKEventStore()

  public var defaultCalendarName: String {
    store.defaultCalendarForNewEvents?.title ?? ""
  }

  public var pendingCount: Int {
    store.pendingWriteCount
  }

  // Completion handlers rather than async/await or Result, because the .mm
  // layer has to turn this into a promise resolve/reject pair and neither
  // `async` nor a Swift enum crosses cleanly into Objective-C.
  public func createEvent(
    title: String,
    startsAt: Double,
    onSuccess: @escaping (String) -> Void,
    onFailure: @escaping (String, String) -> Void
  ) {
    store.requestWriteOnlyAccessToEvents { granted, error in
      guard granted, error == nil else {
        onFailure("E_CALENDAR_PERMISSION", error?.localizedDescription ?? "Access denied")
        return
      }
      let event = EKEvent(eventStore: self.store)
      event.title = title
      event.startDate = Date(timeIntervalSince1970: startsAt / 1000)
      event.endDate = event.startDate.addingTimeInterval(3600)
      event.calendar = self.store.defaultCalendarForNewEvents
      do {
        try self.store.save(event, span: .thisEvent)
        onSuccess(event.eventIdentifier)
      } catch {
        onFailure("E_CALENDAR_WRITE", error.localizedDescription)
      }
    }
  }
}
```

What crosses into Objective-C, and what does not:

| Swift feature | Visible to Objective-C |
| --- | --- |
| `class` inheriting `NSObject` | yes |
| `struct`, `enum` with associated values, generics | **no** |
| `String`, `Int`, `Double`, `Bool`, `Array`, `Dictionary` | yes, bridged |
| `Optional` of a class type | yes, as nullable |
| `Optional` of a value type | **no** — wrap it or use a sentinel |
| `throws` | yes, as a trailing `NSError **` |
| `async` | not in a form the `.mm` layer can use here |
| A closure parameter | yes, as a block |

### 2. The bridging header

A bridging header lets your **Swift** see Objective-C. You need it as soon as the Swift side
references any React Native or Objective-C type. Xcode offers to create one when you add the
first Swift file to an Objective-C target; accept, and it sets `SWIFT_OBJC_BRIDGING_HEADER` for
you.

```objc title=ios/AwesomeProject/AwesomeProject-Bridging-Header.h
// Only Objective-C headers go here. A header that pulls in C++ breaks the
// Swift compiler, and the error will not mention C++.
#import <React/RCTAppDelegate.h>
```

The generated spec header is Objective-C**++**, so it must never appear here.

### 3. The Objective-C++ wrapper

```objc title=ios/AwesomeProject/RCTCalendar.h
#import <AppSpecs/AppSpecs.h>
#import <Foundation/Foundation.h>

NS_ASSUME_NONNULL_BEGIN

// NativeCalendarSpec is the protocol Codegen wrote. AppSpecs is codegenConfig.name.
@interface RCTCalendar : NSObject <NativeCalendarSpec>
@end

NS_ASSUME_NONNULL_END
```

```objc title=ios/AwesomeProject/RCTCalendar.mm
#import "RCTCalendar.h"

// Xcode generates this from the target's Swift files. The name is
// <PRODUCT_MODULE_NAME>-Swift.h and it only exists after a build.
#import "AwesomeProject-Swift.h"

@implementation RCTCalendar {
  Calendar *_calendar;
}

- (instancetype)init
{
  if (self = [super init]) {
    _calendar = [Calendar new];
  }
  return self;
}

// The one genuinely C++ method. It hands back the generated JSI class, which
// is what installs the methods onto the JavaScript object.
- (std::shared_ptr<facebook::react::TurboModule>)getTurboModule:
    (const facebook::react::ObjCTurboModule::InitParams &)params
{
  return std::make_shared<facebook::react::NativeCalendarSpecJSI>(params);
}

// The name JavaScript asks for. There is no export macro in this architecture.
+ (NSString *)moduleName
{
  return @"NativeCalendar";
}

- (NSDictionary *)getConstants
{
  return @{@"defaultCalendarName" : _calendar.defaultCalendarName};
}

- (NSNumber *)getPendingCount
{
  return @(_calendar.pendingCount);
}

- (void)createEvent:(NSString *)title
           startsAt:(double)startsAt
            resolve:(RCTPromiseResolveBlock)resolve
             reject:(RCTPromiseRejectBlock)reject
{
  // Swift's argument labels become part of the selector, which is why this
  // reads as createEventWithTitle:startsAt:onSuccess:onFailure:.
  [_calendar createEventWithTitle:title
                         startsAt:startsAt
                        onSuccess:^(NSString *identifier) { resolve(identifier); }
                        onFailure:^(NSString *code, NSString *message) {
                          reject(code, message, nil);
                        }];
}

@end
```

> [!NOTE] Copy the selectors from the generated header, not from here
> The exact selector for each spec method — argument labels, the promise pair, whether a numeric
> return is `NSNumber *` or `double` — is emitted by Codegen from your spec. Open
> `ios/build/generated/ios/AppSpecs/AppSpecs.h` and match it. On a React Native version other
> than 0.87, that file is the authority.

### 4. Registration

There is no registration code on iOS. The mapping lives in `package.json`:

```json title=package.json
{
  "codegenConfig": {
    "name": "AppSpecs",
    "type": "modules",
    "jsSrcsDir": "src/specs",
    "ios": {
      "modules": {
        "NativeCalendar": {
          "className": "RCTCalendar"
        }
      }
    }
  }
}
```

Codegen turns that into `RCTModuleProviders.mm`, a dictionary from `@"NativeCalendar"` to
`@"RCTCalendar"`, which the runtime looks up by name through `RCTAppDependencyProvider`. A
project created by the Community CLI already installs that provider:

```swift title=ios/AwesomeProject/AppDelegate.swift (the line that matters)
// dependencyProvider is a property of RCTReactNativeFactoryDelegate.
delegate.dependencyProvider = RCTAppDependencyProvider()
```

Two optional keys on the same entry:

| Key | Effect |
| --- | --- |
| `unstableRequiresMainQueueSetup` | The module is constructed on the main queue. Use only if construction touches UIKit. |
| `conformsToProtocols` | Declares that the class also implements an image URL loader, an image data decoder or a URL request handler. |

## How spec types land in Objective-C and Swift

| In the spec | Generated Objective-C | Reasonable Swift |
| --- | --- | --- |
| `string` | `NSString *` | `String` |
| `string \| null` | `NSString * _Nullable` | `String?` |
| `boolean` | `BOOL` | `Bool` |
| `number`, `CodegenTypes.Double` | `double` | `Double` |
| `CodegenTypes.Int32` | `NSInteger` | `Int` |
| `CodegenTypes.Float` | `float` | `Float` |
| An object type | a generated struct, or `NSDictionary *` | `[String: Any]` |
| `ReadonlyArray<T>` | `NSArray *` | `[Any]` |
| `Promise<T>` | `resolve:(RCTPromiseResolveBlock)reject:(RCTPromiseRejectBlock)` | two closures |
| `void` | `void` | `Void` |

Generation for iOS runs with `assumeNonnull` on, so the whole generated header sits inside
`NS_ASSUME_NONNULL_BEGIN`. An optional spec parameter shows up as an explicit `_Nullable`, and
everything else is implicitly non-null. That is worth knowing because a `nil` you pass into a
non-null parameter is a crash rather than a warning.

## Threading

A TurboModule method runs on the JavaScript thread for synchronous methods, and on a background
queue for asynchronous ones. Neither is the main thread, and UIKit requires the main thread.

```swift title=Hopping to the main queue from Swift
public func presentPicker(onDone: @escaping (String) -> Void) {
  // Every UIKit touch — presenting, reading a window, mutating a view — has to
  // be on the main queue, and none of the calls into this class arrive there.
  DispatchQueue.main.async {
    guard let root = UIApplication.shared.connectedScenes
      .compactMap({ $0 as? UIWindowScene })
      .first?.keyWindow?.rootViewController
    else {
      onDone("")
      return
    }
    root.present(self.makePicker(onDone: onDone), animated: true)
  }
}
```

If the module's **construction** needs the main queue — because it builds a `UIView` or reads a
window in `init` — set `unstableRequiresMainQueueSetup` on its `codegenConfig` entry rather than
dispatching synchronously from `init`, which deadlocks.

Promise blocks are safe to call from any queue. Do not wrap a `resolve` in a main-queue hop
unless you need to; you are adding a frame of latency for nothing.

## Errors

`RCTPromiseRejectBlock` takes a code, a message and an `NSError *`. Give it all three where you
have them: the code is what JavaScript branches on, the message is for humans, and the error
carries the domain and user info into the JavaScript error object.

```objc title=Rejecting with a real NSError
- (void)loadCalendar:(NSString *)identifier
             resolve:(RCTPromiseResolveBlock)resolve
              reject:(RCTPromiseRejectBlock)reject
{
  NSError *error = nil;
  NSDictionary *result = [_calendar loadWithIdentifier:identifier error:&error];
  if (error != nil) {
    // The code is stable API; the localizedDescription is not.
    reject(@"E_CALENDAR_LOAD", error.localizedDescription, error);
    return;
  }
  resolve(result);
}
```

On the Swift side, a `throws` function becomes an `NSError **` out-parameter, so
`try store.save(...)` in Swift surfaces as a recoverable error in the wrapper rather than a
trap. A Swift `fatalError` or a force-unwrap of `nil` is a crash the promise never sees.

## Packaging a library for iOS

An app needs nothing: its Swift, its `.mm` and its `codegenConfig` are already part of the
target. A library ships a podspec.

```ruby title=react-native-calendar.podspec
require 'json'

package = JSON.parse(File.read(File.join(__dir__, 'package.json')))

Pod::Spec.new do |s|
  s.name         = 'react-native-calendar'
  s.version      = package['version']
  s.summary      = package['description']
  s.license      = package['license']
  s.authors      = package['author']
  s.homepage     = package['homepage']
  s.platforms    = { :ios => '15.1' }
  s.source       = { :git => 'https://github.com/you/react-native-calendar.git', :tag => "v#{s.version}" }

  # Both the Swift and the Objective-C++ half of the module.
  s.source_files = 'ios/**/*.{h,m,mm,swift}'

  # This is the helper that wires up the New Architecture: React-Core, the
  # codegen output, the folly flags and the header search paths. Do not
  # hand-roll the dependency list.
  install_modules_dependencies(s)
end
```

`install_modules_dependencies(s)` is React Native's own helper, defined in
`scripts/react_native_pods.rb` and available inside any podspec evaluated by a React Native
`Podfile`. It is what keeps a library's build settings in step with the React Native version
the consumer installed.

Autolinking finds the podspec because `use_native_modules!` in the consumer's `Podfile` scans
`node_modules`. The consumer runs `bundle exec pod install` and that is all.

> [!WARNING] Swift Package Manager support is Experimental
> React Native 0.87 can build an app with SPM instead of CocoaPods, and a library can ship a
> `Package.swift` scaffolded with `npx react-native spm scaffold`. The commands and the layout
> may still change between minor versions. CocoaPods remains the default, and a library that
> ships only a `Package.swift` will not install for most consumers. Ship the podspec; add SPM as
> an extra.

## Xcode settings that matter

| Setting | Why |
| --- | --- |
| `SWIFT_OBJC_BRIDGING_HEADER` | Points at your bridging header. Xcode sets it when it creates one. |
| `PRODUCT_MODULE_NAME` | Determines the `<name>-Swift.h` filename your `.mm` imports. Renaming the target renames the import. |
| `DEFINES_MODULE` | Must be on for a framework target so `<name>-Swift.h` is emitted. |
| "Treat incomplete protocol conformance as error" | Off by default. Turning it on makes a missing spec method an error rather than a warning, matching Android. |

That last row is worth doing deliberately. A protocol is not a class: leaving a method
unimplemented compiles, and the failure arrives at runtime as an unrecognised selector.

## Common mistakes

- **Trying to conform to the generated protocol from Swift.** Wrong: `class Calendar: NSObject,
  NativeCalendarSpec`. Right: an Objective-C++ class conforms and forwards. `getTurboModule:`
  has a C++ return type Swift cannot express.
- **Importing a C++ header from the bridging header.** Wrong: `#import "AppSpecs.h"` in
  `AwesomeProject-Bridging-Header.h`. Right: keep every C++ or Objective-C++ header out of it,
  and import them only from `.mm` files. The Swift compiler error will not say "C++".
- **Naming the file `.m` instead of `.mm`.** Wrong: `RCTCalendar.m`, which fails with "this file
  must be compiled as Obj-C++". Right: `.mm`. The generated header says so explicitly at the
  top.
- **Forgetting `@objc` or `NSObject`.** Wrong: a `public class Calendar` that does not inherit
  `NSObject`, so it never appears in `<App>-Swift.h` and the `.mm` file cannot see it. Right:
  inherit `NSObject` and mark members `@objc` (or the class `@objcMembers`).
- **Guessing the Swift selector.** Wrong: `[_calendar createEvent:title startsAt:startsAt ...]`.
  Right: read `<App>-Swift.h` — Swift argument labels become selector pieces, so
  `createEvent(title:startsAt:)` becomes `createEventWithTitle:startsAt:`.
- **Omitting `codegenConfig.ios.modules`.** Wrong: a fully implemented module that
  `getEnforcing` cannot find, while Android works. Right: the iOS registration is configuration,
  not code.
- **Doing UIKit work off the main queue.** Wrong: presenting a view controller directly from a
  promise method. Right: `DispatchQueue.main.async`. The symptom is an intermittent crash, not a
  consistent one.
- **Relying on the Xcode-generated `-Swift.h` before the first build.** Wrong: expecting
  autocomplete to know your Swift class immediately. Right: build once; the header does not
  exist until the Swift target has compiled.
- **Shipping a library with only a `Package.swift`.** Wrong, today: SPM is Experimental in 0.87
  and most consumers are on CocoaPods. Right: ship the podspec, and add SPM alongside it.
