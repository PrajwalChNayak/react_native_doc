A **local module** is an Expo module that lives inside your app repository, in a `modules/`
directory next to your app code, rather than in its own npm package. It uses exactly the same
Expo Modules API as a published module; the only difference is where autolinking finds it.

It is the right default for native code that only your app needs. You get Kotlin and Swift that are
versioned with the JavaScript that calls them, and no package to publish.

> [!NOTE] Expo Go vs development build
> A local module is native code. Expo Go cannot load it. You need a
> [development build](../expo-development-builds/creating-locally.md), rebuilt after every native
> change.

> [!WARNING] The native code on this page was not compiled
> Flags and file layout were read from `create-expo-module@57.0.1` and its template
> `expo-module-template@57.0.11`. The Kotlin and Swift were not built with Gradle or Xcode as part of
> writing this page.

## Why it exists / when to use it — and when NOT to

Use a local module when:

- The native code is specific to this app — a vendor SDK wrapper, a platform API only you need.
- You want native changes reviewed in the same pull request as the JavaScript that uses them.
- You are keeping `ios/` and `android/` generated. Module code in `modules/` is **not** in the
  directories prebuild clears, so it survives regeneration, unlike a hand edit to the app's `android/`.

Do not use a local module when:

- **Several apps need it.** Copying `modules/foo` between repositories diverges quickly. Publish it —
  see [Publishing an Expo Module](publishing.md) — or share it through a monorepo package.
- **The change is configuration, not code.** A permission, a plist key or a Gradle property is a
  [config plugin](../expo-config-plugins/writing-your-own.md), not a module.

## Basic example

From the root of an existing Expo project:

```bash
npx create-expo-module@latest --local
```

The command prompts for a name and the native module name, then writes the module under `modules/`.
Everything it asks can also be passed as flags, which is how you run it in a script:

```bash
npx create-expo-module@latest expo-settings --local \
  --name ExpoSettings \
  --package expo.modules.settings \
  --platform apple android \
  --features Function AsyncFunction Event
```

Then rebuild the native app, because a new module is new native code:

```bash
npx expo run:android
npx expo run:ios
```

Fast Refresh picks up changes to the module's TypeScript. Changes to its Kotlin or Swift need that
rebuild every time.

## How it works

### The flags, verified

From `create-expo-module@57.0.1`'s own option definitions:

| Flag | What it does |
| --- | --- |
| `--local` | Create a local module in the current project, skipping `node_modules` installation and the example app |
| `--barrel` | Generate an `index.ts` barrel file. Applies to local modules only; not generated by default |
| `--name <name>` | Native module name, e.g. `ExpoSettings` |
| `--package <package>` | Android package name, e.g. `expo.modules.settings` |
| `-p, --platform <platforms...>` | Any of `apple`, `android`, `web` |
| `--features <features...>` | Feature examples to include: `Constant`, `Function`, `AsyncFunction`, `Event`, `View`, `ViewEvent`, `SharedObject`, `SwiftUIView`, `SwiftUIModifier`, `ComposeView`, `ComposeModifier`, or `all` |
| `--full-example` | Include every feature example |
| `-s, --source <dir>` | Use a local template directory instead of downloading `expo-module-template` |

`--with-readme`, `--with-changelog`, `--no-example`, `--description`, `--author-*`, `--repo`,
`--license` and `--module-version` exist too, but only matter for a standalone module.

The CLI also has an `add-platform-support` subcommand, documented as adding platform files to an
existing module; it was not exercised for this page.

### What gets generated

The template layout, read from `expo-module-template@57.0.11`, with `ExpoSettings` as the module name:

```text
modules/expo-settings/
  expo-module.config.json
  android/
    build.gradle
    src/main/AndroidManifest.xml
    src/main/java/expo/modules/settings/ExpoSettings.kt
  ios/
    ExpoSettings.podspec
    ExpoSettings.swift
  src/
    ExpoSettings.ts
    ExpoSettings.web.ts
    ExpoSettings.types.ts
```

`index.ts` is added only when you pass `--barrel`. Platform directories you did not select are left
out.

The generated `expo-module.config.json` names one class per platform — the bare Swift class name for
`apple`, the fully qualified Kotlin class name for `android`:

```json title=modules/expo-settings/expo-module.config.json
{
  "platforms": ["apple", "android"],
  "apple": {
    "modules": ["ExpoSettings"]
  },
  "android": {
    "modules": ["expo.modules.settings.ExpoSettings"]
  }
}
```

### How autolinking finds it

Expo Autolinking scans a **native modules directory** for `expo-module.config.json` files, in addition
to your dependencies. In `expo-modules-autolinking@57.0.13` that directory is an option called
`nativeModulesDir`, and its default is `"./modules"`. That default is the only reason a local module
needs no registration anywhere.

To use a different directory, set it under `expo.autolinking` in the app's `package.json`:

```json title=package.json
{
  "expo": {
    "autolinking": {
      "nativeModulesDir": "./native"
    }
  }
}
```

The same `expo.autolinking` object accepts `searchPaths` and `exclude`, and each can also be set per
platform under an `android` or `ios` key; platform values are merged over the shared ones.

### Calling it

The module's TypeScript file is what your app imports, by relative path:

```ts title=modules/expo-settings/src/ExpoSettings.ts
import {NativeModule, requireNativeModule} from 'expo';

export type ExpoSettingsEvents = {
  onChange: (payload: {value: string}) => void;
};

// This declaration is the only description of the native surface the compiler
// sees. Keep it in step with the Kotlin and Swift definitions by hand.
declare class ExpoSettingsModule extends NativeModule<ExpoSettingsEvents> {
  getValue(): string;
  setValueAsync(value: string): Promise<void>;
}

// The string must equal Name("ExpoSettings") in both native definitions.
export default requireNativeModule<ExpoSettingsModule>('ExpoSettings');
```

An app screen then imports it with a relative path such as
`import ExpoSettings from '../modules/expo-settings/src/ExpoSettings';`, or from the barrel if you
generated one.

The `.web.ts` file is resolved instead of `ExpoSettings.ts` when bundling for web, so a module can
provide a JavaScript implementation — or a clear "not supported" error — on that platform.

## Platform differences

:::tabs
@tab Android
- The Kotlin class lives under `android/src/main/java/<package path>/`, and its fully qualified name
  goes in `expo-module.config.json`.
- `android/build.gradle` applies `expo-module-gradle-plugin`, which supplies the shared Android and
  Kotlin configuration. See [Writing a Module in Kotlin](module-in-kotlin.md).
@tab iOS
- The Swift class must be `public`; its bare name goes in `expo-module.config.json`.
- The module ships a `.podspec`, so CocoaPods integrates it on the next native build. See
  [Writing a Module in Swift](module-in-swift.md).
@tab Web
- There is no native code. `src/<Name>.web.ts` is the implementation Metro picks for web builds.
:::

## Common patterns

**One module per capability.** `modules/expo-settings` and `modules/expo-battery`, not one
`modules/native` holding everything. Autolinking handles any number, and each can later be published
on its own.

**Keep the TypeScript surface in the module.** Export a small typed wrapper from `src/` and import that
in the app, so the declaration that must match native code lives beside it.

**Start with `--features` for what you need.** The feature examples are useful references, but
deleting generated examples you never wanted is work nobody does, and dead native code stays in the
binary.

**Move it to a package when a second app needs it.** The directory layout of a local module and a
standalone module is the same, which is what makes the move cheap.

## Security considerations

**Threat.** A local module's functions are callable by any JavaScript in the app, including JavaScript
delivered by an over-the-air update.

**Exploit.** A convenience function such as `readFileAsync(path)` becomes an arbitrary file read for
whoever controls the JavaScript bundle.

**Fix.** Accept identifiers, not paths or raw queries, and resolve them against a fixed base in native
code — the pattern shown in [Writing a Module in Kotlin](module-in-kotlin.md#security-considerations).

**Verification.** Call each exported function from a debug build with hostile input (`../` paths,
empty strings, very long strings) and confirm the native side rejects it with a coded error.

## Common mistakes

- **Editing the app's `android/` or `ios/` instead of `modules/<name>/`.** Prebuild clears and
  regenerates the app's native directories by default; module directories are untouched.
- **Expecting a Kotlin or Swift change to Fast Refresh.** Rebuild with `npx expo run:android` or
  `npx expo run:ios`.
- **Moving `modules/` without setting `nativeModulesDir`.** Autolinking looks in `./modules` by default;
  a module elsewhere is not found, and the error appears at runtime as a missing native module.
- **Short Kotlin class name in `expo-module.config.json`.** Android needs the fully qualified name.
- **Different `Name(...)` strings in Kotlin and Swift.** The module resolves on one platform only.
- **Expecting `index.ts` without `--barrel`.** Import from `src/<Name>.ts`, or regenerate with the flag.
- **Trying it in Expo Go.** It will not load there.
