The App Config

app.json, app.config.ts and app.config.js — the file that describes your Expo app's name, identifiers, icons, plugins and native settings. Which form to use, how they combine, and when dynamic config earns its keep.

Expo SDK 57 · RN 0.86

The app config is the file that describes your app to the Expo toolchain: its name, version, bundle identifier and package name, icons and splash screen, URL scheme, permissions, config plugins and experiments. Under Continuous Native Generation it is the main input from which ios/ and android/ are generated, so for most native settings it is the source of truth rather than Info.plist or AndroidManifest.xml.

It comes in three forms:

FileKindLanguage
app.jsonStaticJSON, config under a top-level expo key
app.config.tsDynamicTypeScript, exports an object or a function
app.config.jsDynamicJavaScript, exports an object or a function

@expo/config also resolves app.config.mts, .cts, .mjs and .cjs, and a static app.config.json — verified from DYNAMIC_CONFIG_EXTS in the installed @expo/config@57.0.9 — but the three above are what you will meet in practice.

Why it exists / when to use it — and when NOT to#

Start with app.json. Both SDK 57 templates ship it, and it has a practical advantage the dynamic forms lack: tools can edit it. npx expo install adds a package's config plugin to plugins for you — but only in a static config. With a dynamic config the CLI cannot safely rewrite your code, so it tells you what to add and you add it by hand.

Move to app.config.ts when the config has to compute something:

  • different bundle identifiers, names or icons per environment (development, preview, production);
  • values read from environment variables at build time;
  • sharing values with other build scripts;
  • conditional plugins.

Do not move to a dynamic config just to get comments or because TypeScript feels more serious. If every value is a constant, app.json is simpler, and tooling can maintain it.

The app config is not a place for secrets

Values under extra, and much of the rest of the config, are embedded in the app and readable at runtime through expo-constants. Anything in the config ships to every user. Never put an API secret there. See What Ships Inside the Bundle.

How it works#

Resolution order#

@expo/config looks for a dynamic config first (app.config.ts, then app.config.js and the other extensions), and a static config (app.config.json, then app.json). When both a dynamic and a static config exist:

  1. the static config is read first;

  2. if the dynamic config exports a function, that function receives the static result as config, and whatever it returns is the final config;

  3. if the dynamic config exports an object, that object is the config and the static file's values are not merged in.

Case 3 is a quiet trap: you add app.config.ts that exports an object, and every value in app.json stops applying. The resolver even tracks this (hasUnusedStaticConfig) so expo-doctor can warn about it.

The dynamic form, typed#

expo/config re-exports @expo/config, which exports both ConfigContext and ExpoConfig. ConfigContext carries projectRoot, staticConfigPath, packageJsonPath and config — the partial config composed from app.json and package.json.

The function runs in Node.js when the CLI resolves the config — during npx expo start, prebuild, run:* and EAS builds. It does not run inside your app.

Common patterns#

Per-environment builds without duplicating the file#

Keep constants in app.json, put only the computed values in app.config.ts using the function form, and set the environment variable per build profile. That keeps npx expo install able to update plugins in app.json.

Native settings the config has no key for#

Reach for expo-build-properties for Gradle and CocoaPods settings, and a config plugin for anything else. Do not edit the generated native files — prebuild regenerates them.

Config changes need a rebuild#

Almost everything in the app config that affects native files — identifiers, permissions, plugins, icons, scheme — takes effect only after regenerating and rebuilding the binary. Reloading JavaScript is not enough, and Expo Go ignores your native settings entirely.

Common mistakes#

  • Exporting an object from app.config.ts while app.json still exists. The static file is ignored. Export a function and spread config, or delete app.json.

  • Expecting npx expo install to add plugins to a dynamic config. It cannot rewrite code; add the plugin yourself when it tells you to.

  • Putting secrets in extra. They ship in the app. Keep secrets on a server.

  • Using process.env values inside app code and expecting the app config's variables. The config function runs in Node at build time. App code sees only what the config put into the resolved config, or EXPO_PUBLIC_ variables — see EXPO_PUBLIC_ Variables.

  • Changing bundleIdentifier or package after release. To the stores that is a different app. Choose them before the first build.

  • Editing Info.plist instead of ios.infoPlist. Under CNG the generated file is replaced on the next prebuild.

  • Copying config keys from an old tutorial. Keys are versioned with the SDK. Check the App Config Reference or the ExpoConfig type.
