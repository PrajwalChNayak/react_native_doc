Writing a Module in Swift

The iOS half of a TurboModule in depth — why Swift needs an Objective-C++ layer, how much of one, type mapping, threading, the podspec and the Experimental SPM path.

RN CLI · 0.87.1

You can write the logic of an iOS TurboModule entirely in Swift. What you cannot do is make Swift the thing React Native talks to. The generated interface is an Objective-C protocol whose methods take and return C++ types, and Swift cannot adopt it.

This page is about that boundary: exactly where it sits, how thin you can make the layer that crosses it, and what the rest of the iOS build needs. It assumes you have read TurboModules End to End, which walks both platforms once.

Why the Objective-C++ layer exists#

Codegen writes two things into ios/build/generated/ios/<name>/<name>.h:

  • @protocol NativeCalendarSpec, with one Objective-C method per spec method plus a getTurboModule: requirement that returns std::shared_ptr<facebook::react::TurboModule> and takes const facebook::react::ObjCTurboModule::InitParams &.

  • class NativeCalendarSpecJSI, a C++ class in namespace facebook::react that holds the JSI bindings.

Swift has no way to express either of those signatures. Apple's Swift/C++ interoperability does not cover std::shared_ptr of a polymorphic C++ type reached through an Objective-C protocol, and the header itself cannot be imported into Swift because it is C++ rather than Objective-C.

So the layering is fixed:

FileLanguageJob
Calendar.swiftSwiftAll of your logic. Knows nothing about React Native.
<App>-Swift.hgenerated by XcodeExposes the Objective-C-visible surface of your Swift
RCTCalendar.h / .mmObjective-C++Adopts the generated protocol, forwards to Swift

The .mm file is small and mechanical: one getTurboModule:, one moduleName, and one forwarding method per spec method. It is not where your logic goes, and it should not grow.

You can skip Swift entirely

If you are comfortable in Objective-C++, put the logic straight in RCTCalendar.mm and delete the Swift file. That removes a file, a bridging header and a generated header from the build. The Swift split is worth it when the logic is substantial or when your team writes Swift; it is overhead when the module is four short methods.

The four files, in order#

1. The Swift class#

What crosses into Objective-C, and what does not:

Swift featureVisible to Objective-C
class inheriting NSObjectyes
struct, enum with associated values, genericsno
String, Int, Double, Bool, Array, Dictionaryyes, bridged
Optional of a class typeyes, as nullable
Optional of a value typeno — wrap it or use a sentinel
throwsyes, as a trailing NSError **
asyncnot in a form the .mm layer can use here
A closure parameteryes, as a block

2. The bridging header#

A bridging header lets your Swift see Objective-C. You need it as soon as the Swift side references any React Native or Objective-C type. Xcode offers to create one when you add the first Swift file to an Objective-C target; accept, and it sets SWIFT_OBJC_BRIDGING_HEADER for you.

The generated spec header is Objective-C++, so it must never appear here.

3. The Objective-C++ wrapper#

Copy the selectors from the generated header, not from here

The exact selector for each spec method — argument labels, the promise pair, whether a numeric return is NSNumber * or double — is emitted by Codegen from your spec. Open ios/build/generated/ios/AppSpecs/AppSpecs.h and match it. On a React Native version other than 0.87, that file is the authority.

4. Registration#

There is no registration code on iOS. The mapping lives in package.json:

Codegen turns that into RCTModuleProviders.mm, a dictionary from @"NativeCalendar" to @"RCTCalendar", which the runtime looks up by name through RCTAppDependencyProvider. A project created by the Community CLI already installs that provider:

Two optional keys on the same entry:

KeyEffect
unstableRequiresMainQueueSetupThe module is constructed on the main queue. Use only if construction touches UIKit.
conformsToProtocolsDeclares that the class also implements an image URL loader, an image data decoder or a URL request handler.

Generation for iOS runs with assumeNonnull on, so the whole generated header sits inside NS_ASSUME_NONNULL_BEGIN. An optional spec parameter shows up as an explicit _Nullable, and everything else is implicitly non-null. That is worth knowing because a nil you pass into a non-null parameter is a crash rather than a warning.

Threading#

A TurboModule method runs on the JavaScript thread for synchronous methods, and on a background queue for asynchronous ones. Neither is the main thread, and UIKit requires the main thread.

If the module's construction needs the main queue — because it builds a UIView or reads a window in init — set unstableRequiresMainQueueSetup on its codegenConfig entry rather than dispatching synchronously from init, which deadlocks.

Promise blocks are safe to call from any queue. Do not wrap a resolve in a main-queue hop unless you need to; you are adding a frame of latency for nothing.

Errors#

RCTPromiseRejectBlock takes a code, a message and an NSError *. Give it all three where you have them: the code is what JavaScript branches on, the message is for humans, and the error carries the domain and user info into the JavaScript error object.

On the Swift side, a throws function becomes an NSError ** out-parameter, so try store.save(...) in Swift surfaces as a recoverable error in the wrapper rather than a trap. A Swift fatalError or a force-unwrap of nil is a crash the promise never sees.

Packaging a library for iOS#

An app needs nothing: its Swift, its .mm and its codegenConfig are already part of the target. A library ships a podspec.

install_modules_dependencies(s) is React Native's own helper, defined in scripts/react_native_pods.rb and available inside any podspec evaluated by a React Native Podfile. It is what keeps a library's build settings in step with the React Native version the consumer installed.

Autolinking finds the podspec because use_native_modules! in the consumer's Podfile scans node_modules. The consumer runs bundle exec pod install and that is all.

Swift Package Manager support is Experimental

React Native 0.87 can build an app with SPM instead of CocoaPods, and a library can ship a Package.swift scaffolded with npx react-native spm scaffold. The commands and the layout may still change between minor versions. CocoaPods remains the default, and a library that ships only a Package.swift will not install for most consumers. Ship the podspec; add SPM as an extra.

Xcode settings that matter#

SettingWhy
SWIFT_OBJC_BRIDGING_HEADERPoints at your bridging header. Xcode sets it when it creates one.
PRODUCT_MODULE_NAMEDetermines the <name>-Swift.h filename your .mm imports. Renaming the target renames the import.
DEFINES_MODULEMust be on for a framework target so <name>-Swift.h is emitted.
"Treat incomplete protocol conformance as error"Off by default. Turning it on makes a missing spec method an error rather than a warning, matching Android.

That last row is worth doing deliberately. A protocol is not a class: leaving a method unimplemented compiles, and the failure arrives at runtime as an unrecognised selector.

Common mistakes#

  • Trying to conform to the generated protocol from Swift. Wrong: class Calendar: NSObject, NativeCalendarSpec. Right: an Objective-C++ class conforms and forwards. getTurboModule: has a C++ return type Swift cannot express.

  • Importing a C++ header from the bridging header. Wrong: #import "AppSpecs.h" in AwesomeProject-Bridging-Header.h. Right: keep every C++ or Objective-C++ header out of it, and import them only from .mm files. The Swift compiler error will not say "C++".

  • Naming the file .m instead of .mm. Wrong: RCTCalendar.m, which fails with "this file must be compiled as Obj-C++". Right: .mm. The generated header says so explicitly at the top.

  • Forgetting @objc or NSObject. Wrong: a public class Calendar that does not inherit NSObject, so it never appears in <App>-Swift.h and the .mm file cannot see it. Right: inherit NSObject and mark members @objc (or the class @objcMembers).

  • Guessing the Swift selector. Wrong: [_calendar createEvent:title startsAt:startsAt ...]. Right: read <App>-Swift.h — Swift argument labels become selector pieces, so createEvent(title:startsAt:) becomes createEventWithTitle:startsAt:.

  • Omitting codegenConfig.ios.modules. Wrong: a fully implemented module that getEnforcing cannot find, while Android works. Right: the iOS registration is configuration, not code.

  • Doing UIKit work off the main queue. Wrong: presenting a view controller directly from a promise method. Right: DispatchQueue.main.async. The symptom is an intermittent crash, not a consistent one.

  • Relying on the Xcode-generated -Swift.h before the first build. Wrong: expecting autocomplete to know your Swift class immediately. Right: build once; the header does not exist until the Swift target has compiled.

  • Shipping a library with only a Package.swift. Wrong, today: SPM is Experimental in 0.87 and most consumers are on CocoaPods. Right: ship the podspec, and add SPM alongside it.
