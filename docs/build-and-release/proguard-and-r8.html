ProGuard and R8

What R8 shrinks in an Android release build, the keep rules React Native and native modules rely on, and why over-aggressive shrinking breaks reflection.

RN CLI · 0.87.1

R8 is the Android shrinker, optimiser and obfuscator that runs on your Java and Kotlin bytecode when you build a release variant with minifyEnabled true. It removes code nothing references, rewrites what is left to be smaller and faster, and renames classes and methods to short strings.

The name "ProGuard" survives in proguardFiles and proguard-rules.pro because R8 consumes ProGuard's rule syntax. ProGuard itself is not what runs. Every rule on this page is a rule R8 reads.

Two things this page is careful about, because both are widely misstated. R8 does nothing to your JavaScript bundle. And R8 is not a security control — it raises the effort of reading your native code and shrinks your app, and that is all.

Why it exists, and what it actually does#

Four separate jobs, each independently controllable:

JobWhat it doesTurned on by
ShrinkingRemoves classes, methods and fields nothing reachesminifyEnabled true
OptimisationInlines, merges classes, removes dead branchesminifyEnabled true
ObfuscationRenames everything not kept to a, b, cminifyEnabled true
Resource shrinkingRemoves unreferenced resources from res/shrinkResources true (requires minifyEnabled true)

The win on a React Native app comes mostly from shrinking your Java/Kotlin dependencies — networking libraries, JSON parsers, analytics SDKs, AndroidX. React Native's own native code is already fairly tight, and the JavaScript bundle is not affected at all.

It is off by default in a generated project#

React Native 0.87.1's template ships this in android/app/build.gradle:

So a stock release build is not shrunk, not optimised and not obfuscated. Turning it on is a deliberate decision, and it is the right one for a shipped app — but make it early in the project, not the week you release. R8 failures surface at runtime in code paths you have not walked.

The generated android/app/proguard-rules.pro is empty apart from comments. That is correct: the rules React Native needs arrive automatically, as explained next.

`proguard-android-optimize.txt`, not `proguard-android.txt`

The template uses the -optimize variant of the default rules file. The non-optimize variant disables R8's optimisation passes. Copying a proguardFiles line from an old tutorial is an easy way to silently turn optimisation off.

The rules you do not have to write#

React Native ships its own consumer ProGuard rules inside the react-android AAR, at ReactAndroid/proguard-rules.pro in the published package. AGP merges consumer rules from every dependency into your build automatically. The real file, read from the installed react-native@0.87.1:

Read what those rules are protecting, because it explains the whole failure mode:

  • native <methods> — JNI resolves native methods by their exact name and descriptor at runtime. Rename one and the lookup fails with UnsatisfiedLinkError.

  • @DoNotStrip — C++ code reaches back into Java by name. Renaming breaks it.

  • implements NativeModule — TurboModules are found by name. A renamed module is a module JavaScript cannot call.

  • @ReactProp methods — Fabric component props are matched by method name.

Every one of these is reflection or name-based lookup across a boundary R8 cannot see. That is the single pattern behind nearly every R8 breakage, in React Native and everywhere else.

Do not copy React Native's rules into your own file

They arrive through the AAR's consumer rules and stay current when you upgrade. A copy in your proguard-rules.pro is a snapshot that silently goes stale — and when it does, the symptom is a runtime crash in a release build, not a build error.

The rules you do have to write#

Anything R8 cannot see a reference to, that something else finds by name.

Your own reflection#

JSON model classes#

Reflection-based parsers (Gson, Jackson, and Moshi's reflective adapter) construct objects by field name. R8 renames the fields, the parser looks for userName and finds a, and every field is silently null — no exception, just empty data.

Codegen-based parsers (Moshi with moshi-kotlin-codegen, kotlinx.serialization) do not need this, because they generate explicit code R8 can follow. Preferring a codegen parser removes the problem rather than papering over it.

Libraries without consumer rules#

Most maintained Android libraries ship their own rules. When one does not, its README usually lists what to add. If it lists nothing and the library uses reflection, that is a signal about the library.

What R8 does not touch#

This is the part that matters most for React Native, and it is the part people get wrong.

Shrunk / renamed by R8?
Your Kotlin and Java codeYes
Android library dependenciesYes
React Native's Java/Kotlin classesPartly — the rules above keep the reflective surface
Your JavaScript bundleNo
Hermes bytecode and its string tableNo
Native .so librariesNo
Assets and the AndroidManifestNo (resources are handled by shrinkResources)

Your JavaScript is minified by Metro, not R8, when it is bundled with --dev false. Hermes then compiles it to bytecode. Neither step encrypts anything, and the Hermes string table is plain data — see Why Secrets in JS Are Readable for the one-command extraction.

Diagnosing a build R8 broke#

The symptoms are distinctive once you know them:

SymptomAlmost always
ClassNotFoundException / NoSuchMethodException in release onlyA reflective lookup on a renamed class
UnsatisfiedLinkErrorA renamed native method
Every field of a parsed object is null, no exceptionA reflection-based JSON parser on renamed fields
A TurboModule is null at import timeThe module class was renamed or removed
A screen renders but a prop does nothingA @ReactProp method was renamed

Step 1 — confirm it is R8#

If the bug disappears, it is R8. If it does not, you are looking at a release-versus-debug difference that has nothing to do with shrinking — a different bundle, a different env file, or __DEV__-gated code.

Step 2 — find out what was removed or renamed#

R8 writes its reports next to the mapping file:

FileAnswers
mapping.txtWhat was renamed to what
usage.txtWhat was removed
seeds.txtWhat was kept, and matched which rule
configuration.txtThe full merged rule set, including every consumer rule

configuration.txt is the one that ends arguments. It shows the rules your dependencies contributed, which is how you discover that a library you suspected already keeps itself.

Search usage.txt for the class in your stack trace. If it is there, it was removed and you need a -keep. If it is only in mapping.txt, it was renamed and you need -keep or -keepnames.

R8 full mode may be the difference

AGP enables R8's "full mode" by default in recent versions. Full mode assumes more aggressively that reflection is absent, so a project that shrank cleanly on an older AGP can break on a newer one. android.enableR8.fullMode=false in android/gradle.properties is the documented escape hatch — treat it as a diagnostic that tells you a missing keep rule exists, not as a fix to leave in place. Confirm the property and its default against the AGP version your project actually resolves, since this behaviour has changed between AGP majors.

Release stack traces and mapping.txt#

Obfuscation makes production crash reports unreadable unless you keep the mapping.

mapping.txt translates that back. Two rules:

  1. Archive mapping.txt for every release you ship, keyed by version. It is regenerated on every build and differs between builds of the same source.

  2. Upload it — to the Play Console with the release, and to your crash reporter, which will then deobfuscate automatically.

Platform differences#

There is no iOS equivalent of R8, and this is worth stating plainly because people ask for one.

  • Swift and Objective-C are compiled to machine code; there is no bytecode to rename.

  • Xcode strips symbols from a Release build (Strip Linked Product, Deployment Postprocessing), which removes debug symbol names but is not obfuscation.

  • You keep the .dSYM for symbolication, exactly as you keep mapping.txt on Android.
  • Your JavaScript bundle on iOS is the same Hermes bytecode, with the same readable string table.

An iOS app is not "more obfuscated" than an Android one. Reaching an iOS app binary is harder — it requires a decrypted IPA — but that is a distribution property, not a code property.

Performance considerations#

  • Size. The saving depends entirely on how much Java/Kotlin dependency code you carry. An app with a large SDK surface can lose a meaningful fraction of its DEX size; an app with almost no Android dependencies saves very little.

  • Build time. R8 adds a non-trivial step to every release build. It does not run on debug builds, so day-to-day development is unaffected.

  • Runtime. Optimisation can help startup slightly by reducing class loading. Treat that as a side effect, not a reason — measure with the tools on Startup Time rather than assuming.

  • shrinkResources true is usually the cheaper win for size and has fewer failure modes than code shrinking, because resource references are easier to track statically. It still requires minifyEnabled true.

Security considerations#

Threat#

An attacker unzips your APK and reads your code to find an endpoint, a key, or a check they want to bypass — a licence check, a root detection, a paywall.

Exploit#

R8 raises the cost of reading Kotlin and Java. It does nothing to the part of a React Native app where your logic actually lives:

Every endpoint, feature-flag name and error message in your JavaScript is in that output, obfuscated build or not.

Fix#

State the honest position:

  • R8 buys size and effort. Renamed identifiers make a decompiled classes.dex slower to read. That is real, and it is worth having.

  • R8 is not encryption. A determined attacker uses a decompiler, works out what the code does from its behaviour, and proceeds. Renaming delays that; it does not prevent it.

  • R8 does not protect your JavaScript at all, which is where a React Native app's logic lives.

So the fix for the underlying threat is architectural, not a build flag: no secrets in the binary, checks enforced server-side, short-lived revocable tokens. See Obfuscation and Its Limits and Why Secrets in JS Are Readable.

Common mistakes#

  • Believing R8 protects your JavaScript. It operates on DEX bytecode only. Your bundle is minified by Metro and compiled by Hermes, and its string table is readable either way.

  • Enabling minifyEnabled the week you ship. R8 breakage appears at runtime in paths you have not walked. Turn it on early and keep a release build in your test rotation.

  • Copying React Native's keep rules into your own file. They come from the AAR's consumer rules and stay current across upgrades. A local copy goes stale and fails at runtime.

  • Fixing a breakage with a whole-package keep rule. A -keep on com.awesomeapp.** works and removes the benefit. Narrow to the class that is actually looked up by name.

  • Using proguard-android.txt instead of proguard-android-optimize.txt. The non-optimize variant turns off R8's optimisation passes, so you keep the breakage risk and lose part of the gain.

  • Setting shrinkResources true without minifyEnabled true. The build fails; resource shrinking depends on code shrinking to know what is unreachable.

  • Not archiving mapping.txt. It is regenerated per build. Once the build machine is gone, every crash report from that release is permanently unreadable.

  • Leaving android.enableR8.fullMode=false in place after debugging. It masks a missing keep rule that will resurface on the next AGP upgrade.

  • Using a reflection-based JSON parser and no keep rules. Fields come back null with no exception, which looks like a backend problem for a surprisingly long time.

  • Assuming iOS has an equivalent. It does not. Symbol stripping is not obfuscation, and the JavaScript is identical on both platforms.
