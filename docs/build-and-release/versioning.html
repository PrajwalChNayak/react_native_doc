Versioning Strategy

Keep versionCode, versionName, CFBundleShortVersionString, CFBundleVersion and your JavaScript release in agreement, automatically.

RN CLI · 0.87.1

A React Native app has five version numbers that can disagree: two on Android, two on iOS, and the one in package.json that your JavaScript reports. Each store enforces different rules about which may repeat and which must increase.

The goal is not a clever scheme. It is that any crash report, any support ticket and any store listing can be traced back to one commit, without anyone having to remember to edit four files.

The five numbers#

WhereNameTypeSeen by usersStore rule
android/app/build.gradleversionCodeIntegerNoMust be strictly greater than every code previously uploaded to any track
android/app/build.gradleversionNameStringYesNo rule; display only
Info.plist → MARKETING_VERSIONCFBundleShortVersionStringDotted stringYesMust increase for each new App Store version
Info.plist → CURRENT_PROJECT_VERSIONCFBundleVersionDotted stringNoMust be unique and increasing within a given short version string
package.jsonversionSemverOnly if you show itNone

The pairing is the same on both platforms: one number humans read, one number the store uses to order builds. Android calls them versionName and versionCode; iOS calls them the short version string and the bundle version. They map onto each other exactly.

React Native 0.87.1's template ships versionCode 1 and versionName "1.0" in android/app/build.gradle, and an Info.plist that already delegates both iOS values to build settings:

That indirection is useful: you never edit Info.plist for a version bump. You change two build settings, which can be set per configuration, overridden on the xcodebuild command line, or written by a script.

Choosing a scheme#

The user-facing version#

Use semantic versioning for versionName and CFBundleShortVersionString, and keep them identical to each other and to package.json. There is no benefit to Android and iOS showing different numbers, and there is a real cost when a support ticket says "version 2.4" and you have two of them.

Resist encoding build metadata here. 1.4.0-rc3+build.882 is legal semver and is not what a user wants to read in the App Store.

The build number#

versionCode and CFBundleVersion need to be monotonic and automatic. Four common sources:

SourceMonotonic?Reproducible from a commit?Notes
Manual incrementOnly if you rememberYesFails the first time two branches release
CI run numberYesNoSimple, reliable; a re-run produces a different number
git rev-list --count HEADUsuallyYesBreaks on shallow clones and can go backwards across rebases
TimestampYesNoWatch the Android integer ceiling — see below

CI run number is the pragmatic default. Commit count is attractive because it is derivable from the source, and it has two sharp edges: CI checkouts are shallow by default (so the count is wrong), and squash-merging a long branch can produce a lower count than a previous build.

Android's `versionCode` has a ceiling, and date-based codes blow through it

Google Play's maximum versionCode is 2100000000. A code shaped like YYYYMMDDHH — 2026091214 — is already above that and is rejected. YYMMDDHHmm overflows too. If you want a date-based code, use something like YYMMDDnn (26091201), and check the arithmetic before you adopt it, because you cannot go back down.

One source of truth#

Put the user-facing version in package.json and derive everything else from it. package.json is already versioned, already reviewed, and already the thing npm version knows how to bump.

Android reads it directly#

Gradle can read package.json at configuration time, so there is nothing to keep in sync:

BUILD_NUMBER defaults to 1 locally, which is fine: a local build never reaches a store, and a hard failure here would block every developer build.

iOS takes them on the command line#

MARKETING_VERSION and CURRENT_PROJECT_VERSION are build settings, so they can be overridden per invocation without touching a file:

Nothing is written to the working tree, so the build is reproducible and the repository stays clean.

If you prefer the values committed, Apple's agvtool edits the project file in place:

agvtool requires CURRENT_PROJECT_VERSION and VERSIONING_SYSTEM to be set in the project; a generated React Native project has the former. It also modifies files, which means a CI build produces a dirty working tree — fine if you intend to commit the bump, awkward if you do not.

Verify what actually shipped#

Do not trust the intent; check the artefact.

Add this as a CI step. It is three lines and it catches "the bump script did not run" before the store does.

Reading the version at runtime#

Crash reports, support screens and analytics all want the version. The reliable source is the native value, because it is what the store actually shipped — a package.json import can drift if your bump script writes one and not the other.

There is no core React Native API that returns the app version. react-native-config can carry it if you put it in the environment file; otherwise a native module such as react-native-device-info (verified on 2026-09-12 as version 15.0.2, peerDependencies react-native: *) exposes getVersion() and getBuildNumber().

The zero-dependency option is to pass the values in through the build:

Whichever route you take, the values must be generated by the same step that sets the native ones. Two independent sources of the version is exactly the problem this page exists to avoid.

Platform differences#

AndroidiOS
Ordering valueversionCode, integer, max 2100000000CFBundleVersion, dotted numeric string
Must increaseAcross every track, foreverWithin a short version string; resets conceptually on a new one
Display valueversionName, any stringCFBundleShortVersionString, must be dotted numeric
Where it is setandroid/app/build.gradleMARKETING_VERSION / CURRENT_PROJECT_VERSION build settings
Per-variant overrideversionNameSuffix, versionCode in a flavourPer build configuration
Enforced atUpload to PlayUpload to App Store Connect

Two asymmetries worth internalising:

  • CFBundleVersion may repeat across different short versions. Uploading 1.5.0 (1) after 1.4.0 (12) is legal. versionCode may never repeat, under any circumstances.

  • CFBundleShortVersionString must be dotted numeric. 1.5.0-beta is rejected. Android's versionName accepts anything, which is why versionNameSuffix "-staging" works on Android and has no iOS equivalent.

Common patterns#

Bump with npm version, let CI do the rest#

CI reads package.json for the display version and its own run number for the build number. No one edits a Gradle file or an Xcode setting by hand, ever.

Never reuse a build number, even for a failed upload#

If an upload fails halfway, bump and rebuild. Both stores remember rejected uploads, and "versionCode 882 has already been used" on a Friday afternoon is a self-inflicted wound.

Tag the commit that produced each store build#

When a crash report names build 882, you need the exact source. A tag is cheaper than archaeology.

Keep the build number the same on both platforms#

Nothing requires it, and it makes every conversation easier: "build 882" means one thing.

Tie the JavaScript version to the native one#

If you ship JavaScript updates outside the stores, the JavaScript payload must know which native binary it is compatible with — a bundle that calls a native module the installed binary does not contain crashes on launch. Key updates to the native version, not to a separate JS version. See Over-the-Air Updates.

Common mistakes#

  • Editing four files by hand. Someone bumps Android and not iOS, and you ship 1.5.0 on one platform and 1.4.1 on the other. Derive everything from package.json.

  • Reusing a versionCode. Play rejects it, including against a build you forgot on internal testing. Never reuse, never decrement.

  • A date-based versionCode above 2100000000. YYYYMMDDHH is already over the limit. Check the arithmetic before adopting a scheme you cannot reverse.

  • git rev-list --count HEAD on a shallow CI clone. The default checkout depth is 1, so the count is 1. Set fetch-depth: 0 — or use the CI run number.

  • A non-numeric CFBundleShortVersionString. 1.5.0-beta is rejected by App Store Connect. Put the qualifier in the build number or the TestFlight notes.

  • Assuming CFBundleVersion is global. It only has to be unique within a short version string, which surprises people in both directions.

  • Reading the version from package.json at runtime. It is bundled JavaScript, not what the store shipped. If the bump script wrote one and not the other, your crash reports lie.

  • Bumping the version in the release PR only. The tag, the store metadata and the changelog then disagree. Bump, tag and release from the same commit.

  • Letting versionNameSuffix reach production. -staging in a flavour is useful; the same suffix applied to prod because it was set on defaultConfig is a visible mistake in the store listing.
