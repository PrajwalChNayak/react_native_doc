Expo Router Fundamentals

File-based routing for React Native, using React Navigation code that expo-router vendors internally. What Expo Router v6 in SDK 57 gives you, what it costs, and the mental model that makes the rest of this section make sense.

Expo SDK 57 · RN 0.86

Expo Router turns the files in your app directory into the routes of your app. A file at app/settings.tsx is the /settings route. A file at app/posts/[id].tsx matches /posts/42. There is no central route table to keep in sync with your screens, because the file system is the route table.

`src/app/`, not `app/`

A project generated by npx create-expo-app@latest on SDK 57 puts the routes in src/app/, alongside src/components/, src/hooks/ and src/constants/, with a @/* path alias pointing at src/. A root-level app/ directory still works and is still found automatically — the router looks in both. This section writes src/app/ because that is what the template produces.

It is not a new navigation engine. Expo Router ships its own copy of React Navigation — the installed expo-router 57.0.21 has no @react-navigation/* dependency and instead vendors core, native, native-stack, bottom-tabs, drawer and elements under build/react-navigation/ — and it exposes React Navigation's stack, tabs and drawer navigators behind a file-based convention. Everything you know about React Navigation's navigation object, screen options and lifecycle still applies — see Migrating from React Navigation.

This section documents expo-router 57.0.21, the version Expo SDK 57 pins. That is the v6 generation. Tutorials written for Expo Router v2 or v3 will be wrong about typed routes, about where Tabs is imported from, and about Stack.Protected, all of which are covered here.

Why it exists / when to use it — and when NOT to#

The problem it solves is drift. In a hand-registered navigator, adding a screen means touching at least three places: the screen file, the navigator, and the param list type. Those three drift apart, and the symptom is a route that exists in the type but not at runtime, or vice versa.

File-based routing removes the drift by removing the duplication. It also gives you two things that are difficult to retrofit:

  • Every screen has a URL. Deep links, universal links and web routes all fall out of the same route tree rather than needing a separate linking config you maintain by hand.

  • Routes are typed from the file system. With typed routes enabled, router.push('/pofile') is a compile error, not a blank screen. See Typed Routes.

Do not reach for Expo Router when:

  • You are adding React Native to an existing native app and navigation is owned by native code. Expo Router expects to own the root of the React tree.

  • Your navigation is genuinely not URL-shaped — a kiosk flow with one screen, or a view that is driven entirely by local state. A single View is not a routing problem.

  • You are on the bare React Native CLI. Expo Router is an Expo SDK package; the CLI half of this site documents React Navigation directly.

Expo Router is included in projects created by create-expo-app with the default template, so in most SDK 57 projects you already have it.

Basic example#

A minimal app is a root layout and one screen.

The default export of a route file is the screen. That is the whole contract.

How it works#

The entry point#

An Expo Router project does not have an App.tsx that you render yourself. package.json points main at expo-router/entry, which mounts the router and hands it a bundler-generated context module containing every file under app/.

This is why routes appear without registration: the bundler enumerates the directory, and the router builds a React Navigation route tree from the filenames.

Filenames are the routing language#

Every routing decision in Expo Router is expressed as a filename. The full set is covered in The app Directory; the shape is:

PatternMeaning
index.tsxthe route for the containing directory
about.tsx/about
[id].tsxa dynamic segment — matches one path part
[...rest].tsxa catch-all — matches the remainder of the path
(group)/groups files without adding a URL segment
_layout.tsxthe layout (navigator) for its directory
+not-found.tsxthe fallback for an unmatched URL
+api.tsa server route, not a screen

Layouts are navigators#

A _layout.tsx file exports a navigator — Stack, Tabs, Drawer, or a bare Slot — and every route file in that directory becomes a screen of it. Nesting directories nests navigators. This is the single most important idea in the section and it has its own page: Layouts.

Navigation has two forms#

Declarative, with Link:

Imperative, with router or useRouter():

Prefer Link where a thing is genuinely a link: it renders a real anchor on web, supports long press previews on iOS, and is accessible by default. Reach for router when navigation is the consequence of an action rather than the action itself. Navigation and Params covers the whole API.

Platform differences#

Expo Router runs on iOS, Android and web from the same route tree, but the three are not the same target:

iOS / AndroidWeb
Route sourcethe same app/ directorythe same app/ directory
URL barnone; URLs arrive as deep linksreal, user-editable, bookmarkable
Stacknative screens via react-native-screensa DOM approximation
+api.ts routesneed a deployed server to callserved by the same origin

On native, a URL is not a thing the user can type — it arrives through a deep link or a universal link, which requires per-platform native configuration. See Deep Links and Universal Links.

Common patterns#

Group your app by layout, not by feature#

Directories in app/ exist to attach layouts and to shape URLs. Files that need the same chrome belong in the same directory; files that need different chrome do not, even if they are the same feature. Use groups when you want the layout without the URL segment.

Keep route files thin#

A route file is a screen, and screens are where routing concerns live: reading params, redirecting, setting header options. Business logic and reusable UI belong in src/ or components/ outside app/, because everything under app/ becomes a route. A app/components/Button.tsx is a /components/Button route, which is almost never what you wanted.

Performance considerations#

  • A _layout.tsx re-renders every screen below it. Keep expensive work out of layouts, or memoise it. A context provider whose value is a fresh object on every render will re-render the whole tree under it.

  • Stack uses native screens. Screens that are off-stack are detached by the native navigator, so their React subtree stops drawing. This is why a timer started in useEffect keeps running on a backgrounded screen while the UI does not — use useFocusEffect for focus-scoped work.

  • Route files are bundled eagerly on native by default. Async routes exist as an opt-in through the expo-router config plugin's asyncRoutes option, and are production-ready on web only. Treat native async routes as experimental.

Common mistakes#

  • Putting non-route files in app/. app/components/Card.tsx becomes the route /components/Card, shows up in the sitemap, and is bundled as a screen. Keep shared code outside app/ entirely.

  • Expecting app/_layout.tsx to be optional when you need providers. Without a root layout the router generates a default Stack for you, and there is nowhere to mount providers. Write one.

  • Copying a v2/v3 tutorial. In the SDK 57 generation, Tabs has moved (see Tabs), typed routes are generated into .expo/types rather than hand-written, and Stack.Protected exists for auth gating. Old snippets compile and then behave wrongly.

  • Treating useRouter() as different from router. They are the same API; useRouter() returns the same object. Use the import outside components, the hook inside them if you prefer hooks-only lint rules.

  • Assuming a screen unmounts when you navigate away. In a stack it does not — it stays mounted below the new screen. Cleanup in useEffect will not run when you expect.

  • Using navigate when you mean push. navigate may pop back to an existing instance of the target route instead of pushing a new one. If you need a new copy every time, use push.
