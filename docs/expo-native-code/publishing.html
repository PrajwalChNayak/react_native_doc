Publishing an Expo Module

Turning an Expo module into an npm package — the create-expo-module standalone layout, package.json fields, building, shipping a config plugin, testing with npm pack, and what consumers must do.

Expo SDK 57 · RN 0.86

A standalone Expo module is an npm package containing Kotlin, Swift and TypeScript that any Expo app can install. Structurally it is the same as a local module plus a package.json, a build step and an example app.

The layout and scripts on this page were read from create-expo-module@57.0.1 and the template it downloads, expo-module-template@57.0.11. The native code was not compiled as part of writing it, and nothing was published.

Expo Go vs development build

A published Expo module contains native code. Apps that install it need a development build; Expo Go cannot load it. Say so in your README.

Why it exists / when to use it — and when NOT to#

Publish when more than one app — yours or other people's — needs the same native code, and copying a modules/ directory between repositories has started to drift.

Do not publish when:

  • Only one app uses it. A local module has no versioning, build or release overhead.

  • Your consumers include React Native apps that do not use Expo, and adding expo to them is not acceptable. An Expo module needs the expo package in the consuming app. A TurboModule does not — see Expo Modules vs TurboModules and Publishing a Native Library, which covers the TurboModule path on React Native 0.87.

  • It is a monorepo with one team. A workspace package gives you the same sharing without a registry.

Basic example#

Without --local, the command creates a standalone package in a new expo-settings/ directory, installs its dependencies, and creates an example/ app that depends on the module. Pass --no-example if the module will live in a monorepo that already has an app to test it in.

Useful flags for a publishable package, all verified in 57.0.1:

The package layout#

package.json, as the template writes it#

The fields that matter, from the template's package.json:

Three things worth understanding:

  • main and types point at build/. Consumers import compiled JavaScript and declarations, not your src/. If build/ is missing from the tarball, the package installs and then fails to resolve.

  • prepare builds it. The template's prepare script deletes and recompiles build/, and also compiles plugin/, cli/, utils/ and scripts/ subdirectories when each has its own tsconfig.json. npm runs prepare before npm pack and npm publish, so a publish always ships a fresh build.

  • expo, react and react-native are peer dependencies. The consuming app provides them. A module that bundled its own react-native would put a second copy in the app.

Template versions are not SDK 57 versions

The template's devDependencies pin versions for the module's own tooling, and some of them are not the versions SDK 57 ships (for example its react-native dev dependency). They affect only the module's local type checking and tests. Consumers always get the React Native their SDK pins, because it is a peer dependency.

What ships#

The template's .npmignore excludes hidden top-level directories, *.tgz, test directories, /internal/module_scripts/, Android test and build output, and /example/. Everything else in the package directory is published — including android/, ios/, src/, build/ and expo-module.config.json, all of which consumers need.

Shipping a config plugin with the module#

If the module needs native configuration in the consuming app — a permission, a plist key — ship a config plugin with it. The resolver looks for app.plugin.{js,cjs,mjs,ts,cts,mts} at the package root:

Consumers then add "expo-settings" to their plugins array. See Writing Your Own Plugin.

Testing the package before publishing#

The example app resolves the module from the parent directory, which is not how a consumer gets it. Test the tarball instead:

This catches the two most common publishing bugs — a missing build/ and a file excluded by .npmignore — before anyone else meets them.

Publishing#

prepare runs first, so the published build/ matches src/.

What consumers do#

Then rebuild their native app. Autolinking finds the package through its expo-module.config.json, so there is no manual linking step. If they keep native directories generated, a new prebuild picks up the module and its plugin.

Platform differences#

  • Consumers build your android/ directory as a Gradle subproject. expo-module-gradle-plugin supplies Android and Kotlin configuration from the consuming app's Expo version, which is what lets one published version work across SDK updates within its supported range.

  • Consumers integrate your ios/ directory through its .podspec. The SDK 57 template's podspec targets iOS 16.4; an app targeting lower cannot install it.

  • src/<Name>.web.ts is compiled into build/ like the rest of src/ and resolved on web builds.

Common patterns#

Support a stated SDK range and test it. Put the supported Expo SDK versions in the README, and run the example app on each before a release. Peer dependencies of "*" do not stop an app on an unsupported SDK from installing your module.

Version native changes as breaking. A change to expo-module.config.json, to a Name(...) string or to a function signature breaks consumers at runtime, not install time. Treat it as a major version.

Keep a changelog. Consumers cannot see from a diff of build/ what changed in Kotlin or Swift.

Security considerations#

Threat. A published module runs native code inside every app that installs it, and its config plugin runs Node code on every developer machine and build server that runs prebuild.

Exploit. An npm account takeover publishes a new patch version whose app.plugin.js exfiltrates environment variables during prebuild, and whose native code adds a network call.

Fix. Enable two-factor authentication on the npm account and require it for publishing. Keep the plugin small and readable so consumers can review it. Do not add install scripts beyond prepare.

Verification. Before publishing, inspect exactly what will ship:

Read the file list. Anything you did not expect to publish — a .env, a keystore, a test fixture with real data — should be removed and added to .npmignore.

Common mistakes#

  • Publishing without build/. main points at build/index.js. Publish through npm so prepare runs, and check npm pack --dry-run.

  • Making react-native a regular dependency. The app gets two copies. Keep it a peer dependency.

  • Telling consumers to use a bare npm install. In an Expo app they should use npx expo install, which resolves versions against their SDK for SDK packages and warns about known incompatibilities.

  • Testing only with the example app. It resolves the module from source. Test the packed tarball.

  • Forgetting the config plugin is part of the public API. Renaming a plugin option breaks consumer prebuilds. Version it like code.

  • Not mentioning that a development build is required. Consumers try Expo Go first and file an issue.

  • Publishing an Expo module as a general React Native library without saying it needs expo. Non-Expo consumers find out at build time.
